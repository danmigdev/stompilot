# Chocolate Plus configuration protocol

Evidence collected on 2026-10-03. This describes controller configuration,
separate from the MIDI commands the controller sends to a TANK Mini or another
effect processor.

## Sources and audit input

The manufacturer's [download page](https://www.m-vave.com/download) lists
FootCtrlPlus under MidiSuite (new). Its
[Windows archive](https://yms-file-store.oss-cn-hongkong.aliyuncs.com/software/pc/MidiSuite_new.zip)
provides the official editor. The configuration wire protocol is not documented
on that page.

The audited AOT image `data/app.so` from the official MidiSuite Windows archive
has SHA-256
`FE74B35619733AAC13ED9522E937472E405AA3B07E96E3F49E4A8E513D429DDD`.
Relevant symbols in this image are:

| Symbol | Address | Evidence |
| --- | --- | --- |
| `UsbConnect.queryNameAndVersion` | `0x5A2C28` | Empty command `0x11`; device name in the first 24 response bytes |
| `UsbConnect.flashRead` | `0x5DD4B8` | Command `0x23`, memory/address/length prefix, matching response prefix |
| `UsbConnect.flashWrite` | `0x5A8BA4` | Command `0x22`, prefix and data, status in command `0x00` reply |
| `SysexCodec.toMidi` | `0x5A3958` | Continuous little-endian bitstream packed into 7-bit MIDI data |
| `FcpModel.setData` | `0x630CB4` | Reads the configuration fields and advanced bank groups |
| `FcpModel.exportData` | `0x62E2A0` | Serializes the complete configuration image |
| `AdvCustomStruct.encodeForBle` | `0x5E14B4` | Advanced switch bank serialization |
| `AdvCustomStruct` constructor | `0x6C7C54` | Builds the same bank fields when decoding |

`_FootCtrlPlusDesktopPageState._writeAdv` passes the bank serialization to its
write method, which calls the native USB configuration operation.

The independent configurator's original author also publishes
[protocol.js](https://gdrums-chocolate.vercel.app/js/protocol.js) and
[pedal.js](https://gdrums-chocolate.vercel.app/js/pedal.js). These corroborate
the raw command/checksum format and the proprietary BLE channel
`AE40` / write `AE41` / notify `AE42`. Their 1,858-byte CubeSuite memory image
is an older layout and must not be used for Stompilot's advanced page layout.
Stompilot does not copy this implementation or offer a BLE connection.

## USB wire format

Before MIDI packing, each packet contains:

| Field | Encoding |
| --- | --- |
| Header | `00 59` |
| Command | One byte |
| Payload length | Three bytes, little endian |
| Payload | Exactly the declared length |
| Checksum | `(~sum(payload)) & 0xFF` |

Treat the entire raw packet as a little-endian bitstream, emit successive 7-bit
groups, then enclose them in `F0` and `F7`. Emit a final group only when bits
remain. This differs from the redundant zero group generated by the TANK
compiler when the bit count is exactly divisible by seven.

* Query: command `11`, empty payload; reply command `11`.
* Read: command `23`; payload is memory type (one byte), address (four bytes,
  little endian), length (three bytes, little endian). The reply repeats this
  eight-byte prefix before the returned data.
* Write: command `22`; the same prefix followed by data. Reply command `00`
  contains status `00` for success.

Use memory type `04` and offsets within the configuration image. MIDI Suite's
nominal read/write chunks are 1,009/1,024 bytes. The connected V16 controller
answered 512-byte reads but did not answer requests for 896, 1,008, or 1,009
bytes. Stompilot therefore uses 512-byte chunks for both operations; the write
size has been checked with simulated controller responses.

## Configuration map

The official editor reads 23,646 bytes at offset zero. A full read from the
connected `FootCtrlPlus_016` corroborates this map and its bank serialization.

| Offset | Meaning |
| --- | --- |
| `0` | Operating mode; `03` selects Advanced Custom |
| `1`–`92` | Other controller settings, preserved |
| `93`–`13436` | Eight advanced pages, four switches per page, 417 bytes per switch |
| `13437`–`23636` | Other keyboard and mixed custom settings, preserved |
| `23637`, `23638` | PC and CC group limits, preserved |
| `23639` | Advanced group count minus one |
| `23640` | Current advanced group |
| `23641`–`23645` | Remaining settings bytes, preserved |

Each advanced switch has one mode byte, 16 five-byte MIDI rows for Bank A,
16 rows for Bank B, 128 SysEx bytes for Bank A, and 128 for Bank B. A row stores
enabled, MIDI channel, type, data 1, and data 2. Controller pages and a switch's
alternating banks are separate concepts.

The type byte is `00` for Program Change (data 1 is the program number), `01`
for CC, and `04` for SysEx. MidiSuite fills unused rows of a fresh controller
with enabled Program Change 0 rows. On 2026-10-16 a `FootCtrlPlus_013` row
`01 00 00 04 00` sent `C0 04` over USB, which loaded TANK preset 2B.

A SysEx bank has one enabled row `01 00 04 00 00` (enabled, channel 1, type 4).
Its 128-byte SysEx area is:

| Byte | Contents |
| --- | --- |
| `0` | Length `n` of the bytes to send, at most 127 |
| `1`–`n` | Sent exactly as stored: complete `F0`…`F7` messages, back to back |
| `n+1`–`127` | Zero |

The firmware does not add `F0`. Bank A of a switch that turns MOD on is
`15 F0 00 32 09 49 00 00 00 02 0A 00 00 00 11 00 00 00 01 3E 03 F7 00 …`.
This was checked on the wire on 2026-10-15 with a `FootCtrlPlus_013`: with
`F0` in byte 0, the controller sent nothing; with a length byte but no `F0`,
it sent the bytes unchanged, which arrived as CCs; with `[n] F0 … F7`, every
frame arrived valid. MidiSuite's SysEx field hides byte 0, and text typed there
without `F0` is sent without it.

Stompilot v0.3.2 and earlier wrote the messages from byte 0. `F0` is never a
valid length, so those banks are recognized on read and rewritten on the next
write.

The owned implementation is in `midi_configurator/chocolate.py` and
`midi_configurator/chocolate_transport.py`. The transport writes only changed
spans from a previously read image. It checks that image again before writing,
requires successful status and immediate readback for each span, writes the
group settings and operating mode last, and verifies the full final image.
The UI saves a backup before invoking this operation. This is a sequence of
verified writes, not an atomic controller transaction.

## Validation and limits

A read-only hardware check confirmed the identity response and complete
configuration layout:

* Device: `FootCtrlPlus_016`, firmware 16.
* Size: 23,646 bytes.
* Real hardware operations: identity query and configuration reads only;
  **zero configuration writes**.

Raw controller snapshots and device-discovery metadata are not included in the
repository. Regression tests generate deterministic controller fixtures.

Twelve transport tests exercise a memory-backed controller: packet length,
identity and port guards, chunked reads, mismatched response prefixes, sparse
writes, stale snapshots, rejected/lost acknowledgements, incomplete responses,
full readback differences, timeouts, and port cleanup. Since then, the
transport has written physical controllers with a matching full readback, and
a `FootCtrlPlus_013` forwarded three consecutive TANK frames from one bank over
USB. Forwarding in host mode to a TANK on the HOST port remains to be
validated. Bluetooth configuration is not implemented.
